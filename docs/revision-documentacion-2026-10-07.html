Historia y trabajo comercial

CAP/EXP, datos originales, investigaciones, planes y seguimiento no son basura. Se conservan fuera del recorrido de lectura obligatorio, con fecha y estado explícitos.

No usar todavía como fuente autónoma para un despliegue o una propuesta comercial. El README atribuye al presente una capacidad medida con Qwen; la configuración local usa Gemma. La migración omite los pesos de Gemma montados desde fuera del repo. El SLA es un borrador no versionado con compromisos que el stack inspeccionado no acredita.

Recorte concreto: sacar del núcleo operativo REFACTOR.md (788 líneas), la investigación de hardware de tres GPUs (187) y la descripción técnica histórica de Browix (183): 1.158 líneas que pueden quedar como archivo o contexto de cliente. No se propone perder su evidencia.

Una corrección documental no arregla los riesgos de ejecución. Los bloqueantes de seguridad, tenencia y operación están en el informe de producción anterior.

Qué no coincide con el estado actual

Ordenado por riesgo de tomar una decisión equivocada. Abrí cada punto para ver el contraste y la corrección propuesta.

D01 · urgenteLa capacidad vigente está atribuida al modelo equivocado

Documentado: README presenta Qwen3.5-9B, compose «sin override» y ~32 llamadas con p95 ≤ 3 s. El índice de capacidad llama vigentes a esos resultados.

Contraste: la configuración local selecciona docker-compose.gemma4-26b.yml; ese override fija Gemma 26B, contexto 16.384 y 32 secuencias. CAP-001 mide Qwen, no Gemma; además solo registra base y rampa. AGENTS ya advierte que Gemma no tiene capacidad medida.

Propuesta: un único encabezado de estado con modelo, override, fecha y CAP compatible. Conservar CAP-001 como medición válida de otra configuración, sin trasladar su techo al modelo actual.

Fuentes: README:78–94; capacity/README:7–13; override:14–37; AGENTS, capacidad con Gemma; .env:30,91 (solo claves no secretas inspeccionadas).

D02 · urgenteMigrar siguiendo el runbook no reproduce el LLM actual

Documentado: el runbook da un COMPOSE_FILE sin Gemma y copia Qwen y Parakeet del volumen de Hugging Face. Afirma que los pesos se descargan solos.

Contraste: el override actual carga Gemma desde /models/gemma-4-26B-A4B-it-qat-AWQ-INT4, con un bind mount de /home/laureano/Models. Ese directorio externo no figura en el inventario ni en backup.sh. Copiar repo, .env, base y checkpoint TTS no basta. También quedó pendiente «commitear WhatsApp SIP», pero esos archivos ya están versionados; la migración más reciente es 0008, no 0007.

Propuesta: inventariar el modelo local con origen, revisión/checksum, permisos y ruta configurable; distinguir restauración de descarga reproducible. Actualizar precondiciones y checkpoint de esquema. No reemplazar un inventario del host por valores genéricos.

MIGRACION_SERVER:27–51,142,212,243–253,476; override:21–37; backup:24–29; migración 0008; comprobación con git ls-files.

D03 · urgenteLa receta de entrenamiento puede elegir la GPU ocupada por el LLM

La guía indica liberar TTS y entrenar en GPU 1, pero sus comandos llaman a ./run.sh sin fijar GPU. El lanzador usa GPU=0 por defecto. La instrucción del agente tts-finetune todavía dice «TTS, GPU 0». El compose vigente asigna LLM a 0 y TTS/STT a 1.

Propuesta: la receta debe exigir selección explícita de GPU después del inventario y la autorización de parada. Centralizar el reparto; no duplicarlo en el agente. No se ejecutó entrenamiento ni se detuvo ningún servicio.

TTS_FINETUNE:53,87–94,129–141; agente:23–25; run.sh:19; compose, device_ids.

D04 · urgenteEl borrador de SLA describe una infraestructura aún no acreditada

El archivo tiene notas internas de borrador dentro de un comentario HTML —invisible al renderizar Markdown—, pero el cuerpo promete 99,8%, dos sitios, UPS, conectividad dual, réplica, backup externo y monitoreo desde tres ubicaciones. También menciona grabaciones. El repo describe un solo servidor; PRODUCCION deja redundancia y monitoreo externo como pendientes. No se verificó infraestructura externa adicional.

Propuesta: conservarlo como borrador visible, no aprobado, fuera de la documentación vigente. Vincular cada compromiso a una evidencia operativa antes de publicarlo. El archivo es trabajo ajeno no versionado: no se modificó. Esta observación es técnica, no una revisión jurídica.

SLA:1–9; §§3,4,6,9,13; PRODUCCION §§3–6; healthcheck; backup.

D05 · urgenteLas guías contradicen el ruteo multi-número y el caller ID

GUIA_UI dice que una cuenta de Anura no informa el DID y que se necesita una cuenta distinta por número; además dice que el caller ID siempre es el global. ARQUITECTURA repite el destino único. El dialplan normaliza el DID recibido y el caller ID enviado por LiveKit; solo cae a ANURA_DID cuando no obtiene un valor válido. TELEFONIA documenta esta verificación desde el 29-sep, pero conserva pasos antiguos que dicen lo contrario.

Propuesta: una única descripción del contrato Anura → DID → tenant/agente y del fallback, con pruebas para varios DIDs. La guía del usuario solo debe indicar qué puede elegir y cuándo falla; no recomendar cuentas adicionales por una limitación retirada.

GUIA_UI:121–125,173,319; ARQUITECTURA, entrantes; TELEFONIA:30–47; extensions.conf:31–40,109–123.

D06 · importanteWhatsApp tiene varias versiones del estado de despliegue

D11 · importanteEstado y cierre de WhatsApp no coinciden entre las guías

ARQUITECTURA dice que se reutiliza una conversación «no completada». El servicio selecciona un hilo abierto dentro de la ventana de actividad; no exige que el motor siga active. WHATSAPP_PLAN explica correctamente que después de [FIN] un mensaje puede retomar el historial. El cierre manual, el vencimiento del hilo y el estado del workflow son cosas diferentes.

Propuesta: documentar estas tres condiciones y qué agente/versión atiende al reabrir. Eso evita interpretar «completed» como una pausa, una baja o una conversación imposible de retomar.
